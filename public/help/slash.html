/mattermost-request-hub channel

On its own, opens the Request a Channel form. With a prefix and a channel name, it requests the channel in the current team without the form.

Requesting a channel without the form

/mattermost-request-hub channel <prefix> <Channel name> [--suffix <suffix>] [--purpose <text>] [--private] [--members @user ...] [--admins @user ...] [--category <name>]

The prefix comes first, typed exactly as /mattermost-request-hub prefixes lists it (for example team-). Then comes the channel name, which can be several words, then any options in any order. Each option takes the words up to the next --, and each can be given only once.

OptionWhat it does
--suffix <suffix>The URL part after the prefix, as one word. Leave it out to generate it from the channel name.
--purpose <text>A short description of the channel.
--privateMakes the channel private. Without it the channel is public.
--members @user ...Users who become regular members on approval. If you list exactly one member and no --admins, that member is made a Channel Admin, so the channel always has someone who can manage it.
--admins @user ...Users who become Channel Admins on approval.
--category <name>Sidebar category to place the channel in on approval. It can be several words; a missing category is created.

For example:

/mattermost-request-hub channel team- Marketing Team --purpose Campaign planning --members @alice @bob --admins @carol
/mattermost-request-hub channel ops- SRE On-call --suffix sre-oncall --private --category Operations

The request goes through the same checks and approval as the form, and you get the same confirmation.

Limits of the command

A channel name, purpose or category can't contain a word that starts with --, and extra spaces or line breaks in them become single spaces. Use the form if you need either.

/mattermost-request-hub channel-admin

On its own, opens the Request Channel Admin form. With @user names, it files the request for the channel you run it in.

Requesting Channel Admin without the form

/mattermost-request-hub channel-admin @user [@user ...]

Run it in the channel itself. You must be a member of it (System Admins excepted), and everyone you name must already be a member too; the request never adds anyone to the channel. The request goes to the System Admins and the Team Admins of the channel's team, the same approvers as the form. The command isn't hidden from people who already admin the channel, but they can manage it directly instead.

ReplyWhat to do
Name at least one channel member...Add at least one @user.
everyone you nominate must already be a member of the channelAdd them to the channel first.
channel not found, or you are not a member of itRun it from a channel you belong to.
Channel Admins can only be requested for public or private channels, that channel is archivedDirect and group messages and archived channels can't have Channel Admins.
you already have a pending Channel Admin request for these people in this channelWait for the existing request to be reviewed.

/mattermost-request-hub prefixes

Lists every prefix your admin configured, with its description and, where there is one, its suffix rule. Use these exactly with /mattermost-request-hub channel.

/mattermost-request-hub list

Lists the channel and Channel Admin requests you made that are still waiting for review, oldest first. Each line shows what you asked for, the day you submitted it (in UTC), the day it expires if your admin set an expiry, and its request ID. A request that expired before anyone reviewed it is shown as expired (an approver can close it). A request submitted before the plugin started recording submission times shows submitted before the upgrade and doesn't expire. If nothing is waiting, the reply is You have no pending channel or Channel Admin requests.

At most 50 requests are shown, followed by ...and N more when there are others. A type a System Admin turned off isn't listed; with both turned off the reply is Channel and Channel Admin requests are currently disabled by an administrator. Approved and denied requests aren't listed: the outcome arrives in your request's direct message thread. Other request types (teams, bots, webhooks and so on) aren't listed yet.

/mattermost-request-hub approve

/mattermost-request-hub approve <request ID>

Approves a channel or Channel Admin request without clicking its card. The request ID is at the bottom of the approval card, after Request ID:, and in the requester's own copy of the request. The command makes the same checks as the Approve button, in the same order, and the reply is only visible to you. When it succeeds, the approval card is closed with the outcome, the same as after a click, and the requester's request thread is updated. When the request went to System Admins by direct message (no approval channel), every copy is closed. See Approving for who can approve.

Like the card buttons, approve and deny still work on a request whose type a System Admin turned off after it was submitted, so pending requests can be closed.

/mattermost-request-hub deny

/mattermost-request-hub deny <request ID>

Denies a channel or Channel Admin request, as its Deny button would. It works the same way as approve.

/mattermost-request-hub exercise

/mattermost-request-hub exercise populate
/mattermost-request-hub exercise status
/mattermost-request-hub exercise teardown

Exercise mode fills a team with believable, clearly marked data for training and demonstrations. Only System Admins can run it, and only while Enable exercise mode is on in System Console → Plugins → Mattermost Request Hub. Run it from a channel in the team you want to seed. Each team has its own exercise data. populate also needs Allow channel requests on and at least one channel prefix, and Allow channel admin requests on when the scenario has Channel Admin requests. status and teardown work whatever those settings are, so exercise data can always be removed.

SubcommandWhat it does
populateCreates the scenario's personas, its channels and its pending requests. Each request gets its approval card, in the approval channel the team's real requests use (or as direct messages to System Admins when there is none), and its persona gets the usual request thread. Runs once per team until teardown.
statusCompares what populate recorded with what is still live: active personas, channels not archived, and requests still pending.
teardownCloses the exercise requests still pending, marking their approval cards and the personas' request threads, archives every exercise channel (including any created by approving an exercise request), deactivates the personas, and removes what the plugin stored about the exercise requests.

Everything exercise mode creates is marked:

  • Personas have the nickname EXERCISE and a position that starts with EXERCISE:. They get a random password that is never shown, so nobody can sign in as one, and email notifications are off.
  • Channel names shown in the sidebar start with EXERCISE, purposes start with [EXERCISE], and each exercise channel's header is an EXERCISE banner.
  • Approval card titles start with EXERCISE, and the message above the card starts with EXERCISE: (after the team label, when the card is routed for another team) and mentions nobody, so populate doesn't notify the approvers.
  • Audit cards and the personas' request threads about exercise requests start with EXERCISE.

Seeded requests are made by personas and name only personas, so approving one gives no real user access to anything. Approve and deny work exactly as for a real request, on the card or with approve and deny. Seeded requests don't count toward any real user's pending limit. Channel names use the first configured prefix and must pass its suffix rule.

Teardown only touches what exercise mode created: the requests, channels and persona accounts it recorded. Real requests, channels and accounts are left alone, even ones that use an exercise name. Teardown waits while a populate is still running in the team.

Nothing is deleted outright

Mattermost doesn't let plugins delete users or channels. Teardown archives exercise channels, renaming each first so the name can be used again, and deactivates the personas. The next populate reactivates the same personas.

The exercise scenario

The plugin includes a fictional scenario. To seed your own personas, channels and requests, paste a scenario into Exercise scenario (JSON) in the plugin settings. It is stored only in this server's configuration. A scenario looks like this: 

{
  "id": "sample",
  "name": "Sample",
  "personas": [
    {"role": "lead", "first_name": "Ana", "last_name": "Lee", "position": "Shift lead"},
    {"role": "crew", "first_name": "Bo", "last_name": "Ng", "position": "Crew member"}
  ],
  "operations": [
    {"act": 1, "operation_id": "ops-channel", "kind": "channel", "suffix": "ops",
     "display_name": "Ops", "purpose": "Shift coordination", "requester": "lead", "members": ["crew"]},
    {"act": 1, "operation_id": "plans-request", "kind": "channel_request", "suffix": "plans",
     "display_name": "Plans", "purpose": "Planning", "private": true, "requester": "crew",
     "members": ["lead"], "age_days": 45},
    {"act": 1, "operation_id": "ops-admin", "kind": "admin_request", "channel": "ops-channel",
     "requester": "lead", "nominees": ["crew"]}
  ]
}
FieldMeaning
id, nameRequired. The name appears in the populate reply.
personasThe people in the scenario, at most 50. role is a short lowercase key that becomes part of the username (exercise-<role>-<team>).
act, operation_idIdentify each operation, at most 200. Operation IDs must be unique.
kindchannel creates an exercise channel at once. channel_request files a pending channel request. admin_request files a pending Channel Admin request on an earlier channel operation, named in channel.
requester, members, admins, nomineesPersona roles, at most 100 in each list. For a channel, requester creates it.
suffix, display_name, purpose, privateAs in a real request. The suffix follows the first configured prefix.
age_daysOptional, from 0 to 3650. Backdates a request, for example past the expiry so its card shows as expired when approved.

Forms for the other request types

These subcommands take no arguments and open the request form for their type. The form, approvers and what happens on approve are described on each type's page.

/mattermost-request-hub team

Opens the Request a Team form. See Teams.

/mattermost-request-hub team-admin

Opens the Request Team Admin form for the current team. See Teams.

/mattermost-request-hub team-member

Opens the Request Team Members form for the current team. See Team members.

/mattermost-request-hub team-guest

Opens the Request Guest Invite form for the current team. See Guest invites.

/mattermost-request-hub bot

Opens the Request a Bot form. See Bots.

/mattermost-request-hub webhook-incoming

Opens the incoming webhook form. See Webhooks.

/mattermost-request-hub webhook-outgoing

Opens the outgoing webhook form. See Webhooks.
