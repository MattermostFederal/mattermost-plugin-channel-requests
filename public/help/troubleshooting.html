Troubleshooting

What a message means, and what to do about it.

"Channel requests aren't configured yet"

/mattermost-request-hub channel, /mattermost-request-hub prefixes and the Agents list_prefixes tool show Channel requests aren't configured yet. Ask a System Admin to define at least one channel prefix in System Console → Plugins → Mattermost Request Hub. A channel request submitted from the form or the Agents request_channel tool is refused with plugin is not configured: an admin must define at least one channel prefix.

Cause: no channel domain prefix is defined. Every channel request needs one. Fix: a System Admin adds at least one prefix under Channel domain prefixes, for example with Load preset.

"... requests are currently disabled by an administrator"

Cause: a System Admin turned that request type off in the plugin settings (for example Allow channel requests or Allow channel admin requests). The type is hidden from the Request Hub and the server refuses it from every entry point. Fix: ask a System Admin to turn it on if you need it.

Requests arrive as direct messages to System Admins

Cause: no approval channel could be used for a channel or Channel Admin request: Approval team isn't set, or the team can't be found, and the request's team has no per-team approval channel. Rather than drop the request, the plugin sends it by direct message to every active System Admin, and the server log has the warning no approval channel available.

Fix: set Approval team in the plugin settings to the name of an existing team. The plugin creates its approval channels there. Any one System Admin can act on a DMed request; after that, the other copies are closed with the outcome. A copy sent before the plugin was upgraded to this version keeps its buttons, which reply This request has already been handled.

If no System Admin can receive the message either, the requester sees could not send your request to the approvers; try again or contact a System Admin.

"This request has expired"

Cause: the channel or Channel Admin request wasn't reviewed within Request expiry (days). Approve and Deny, on the card or with the slash command, both reply This request has expired., the card is marked ⌛ Expired: not reviewed within N days., and the requester's ticket is closed as expired.

Fix: the requester submits it again. Raising the expiry also applies to requests already pending; 0 turns expiry off. See Expired requests.

"You have N pending requests waiting for review"

Cause: the requester is at Pending requests per user for that kind of request (new channels and Channel Admins are counted separately). Expired requests no longer count.

Fix: wait for an approver to act on some, or for them to expire. A System Admin can raise the limit, or set it to 0 for no limit.

A related message, you already have a pending request for ~name in this team (or you already have a pending Channel Admin request for these people in this channel), means the same request is already waiting. It doesn't need to be submitted twice.

Approve says the requester is no longer active or a member

Approve checks the request again before acting. You'll see a private message, and the request stays pending with its buttons:

  • The requester's account is no longer active. Deny this request instead.
  • The requester is no longer a member of the team. Deny this request instead. (channel requests)
  • The requester is no longer a member of the channel. Deny this request instead. (Channel Admin requests)
  • The channel name no longer matches the configured prefixes. Deny this request and ask the requester to submit it again.

Fix: deny the request. Deny is never blocked. See Approving.

For a Channel Admin request, if the nominees have left the channel by the time it's approved, the card says nobody was promoted: the nominees are no longer members and the requester is told.

"Try again" messages

Could not check the requester right now. Try again in a moment., could not load your account; try again and could not save your request; try again mean a lookup or save failed for a moment.

Fix: try again. If it keeps happening, check the server log for an error from the plugin.

No cards in the audit channel

Cause: the plugin posts every approve, deny and expiry to the private mattermost-audit-requests channel it creates in the approval team. Without an Approval team (or when the team can't be found) there is no audit channel and nothing is posted; the server log has cannot ensure named approval channel. If the channel exists but a post fails, the log has audit post failed with the reason.

Fix: set Approval team to an existing team. System Admins are added to the audit channel automatically.

Agents tools not showing

If an agent doesn't offer to file channel requests, check, in order:

  • Offer tools to Agents is on in the Mattermost Request Hub settings. It's off by default.
  • The Mattermost Agents plugin is installed and enabled, on Mattermost 11.3 or later.
  • Allow channel requests and Allow channel admin requests are on; a tool for a type that's off refuses with the disabled message.
  • The tools are allowed in the Agents plugin's settings. They're listed with this plugin's prefix: com_mattermostfederal_mattermost-plugin-request-hub__list_prefixes, com_mattermostfederal_mattermost-plugin-request-hub__request_channel, com_mattermostfederal_mattermost-plugin-request-hub__request_channel_admin, com_mattermostfederal_mattermost-plugin-request-hub__list_my_requests and com_mattermostfederal_mattermost-plugin-request-hub__get_request_status.

See AI agents for what each one does.

Exercise mode

These are replies to /mattermost-request-hub exercise.

"Exercise mode is off": turn on Enable exercise mode in System Console → Plugins → Mattermost Request Hub. Only System Admins can run the command.

"exercise mode seeds channel requests, which are turned off" or "this scenario seeds Channel Admin requests, which are turned off": populate files the same requests a user would, so it needs Allow channel requests (and Allow channel admin requests for a scenario with Channel Admin requests) on. Nothing was created. status and teardown don't need either setting.

"The username @exercise-... is taken by an account that isn't exercise data": a real account has a persona's username. Populate creates nothing in that case. Rename that account, or change the persona's role in the exercise scenario.

"This server or team only allows accounts with email addresses at ...": personas use addresses at exercise.invalid, a domain that never receives mail, and Mattermost only lets accounts from the allowed domains join a team. While you run the exercise, add exercise.invalid to Restrict account creation to specified email domains in the System Console, or to the team's allowed domains, whichever the reply names.

"A channel named ~... already exists in this team": a channel, archived or not, already has a name the scenario needs. Rename it, or change the scenario's suffix.

Status says the exercise is populating when no populate is running: an earlier populate stopped partway. The server log has failed to populate exercise data with the reason. Run /mattermost-request-hub exercise teardown, which removes whatever it created, then populate again. For five minutes after a populate stops, teardown answers a populate is still running in this team, since it can't tell a stopped populate from a slow one. Wait and run it again.

Teardown says some items could not be removed, or status says a teardown started but didn't finish: the record of the exercise is kept, so run teardown again. The server log names each item that failed. A request stored under an exercise request's ID that isn't exercise data is always left alone and reported this way.
